# 链模型与 `_` 绑定决策

对应 [spec/04-链模型](../spec/04-链模型-CHAIN.md)。

## 禁 `_` 多引用的三条理由

1. **隐式 mutation 风险**：先求值的成员若含变异调用，后续成员读到的是变化后的值——引用越多越难推断；
2. **功能可替代**：多视图需求用链上定义完全覆盖（`data -> def d -> match _ {…}, d -> @fn`）；
3. **从严到宽是安全演进**：将来放开多引用不破坏任何既有代码；反之收紧则是 breaking change。

先例：Kotlin `it` / Clojure `%` 支持多引用；Scala `_`（每处独立绑定）因语义混乱被社区弃用。Cosat 取最保守形态。

## `data -> @fn1, data2 -> @fn2` 工作结论

按点位模型推导为 `fn2(fn1(data), data2)`（首段 `@fn1, data2` 为合并段）。该推导自洽且无歧义，但属实现前的推演结论，最终以编译器行为为准（❓ 待定案，见 spec/05 §6.6 与 spec/11）。

## 点位校验按跳进行

点位总数 = 左侧参数数量的校验**逐跳执行、不跨 `->` 累加**：每跳的左侧是该跳上游的实际产出（可能是上一跳的结果组），跨跳累加既无语义对应也无法在编译期确定。

## 逐位消费取代恰一次引用（2026-08-24）

「禁 `_` 多引用」三条理由复核后部分失效，原定案被取代：

1. **mutation 风险**：新模型下合并段各 `_` 是相互独立的消费槽（各吃一个上游值），不存在共享绑定，该风险结构性消失；
2. **可替代性**：单值多视图仍走链上定义中转（不变）；但多个上游值的各自直通（`data1, data2 -> _, _ -> @fn`）此前无法匿名表达，对一次性管道而言具名样板是纯噪音；
3. **从严到宽**：本放宽正是上文预留的安全演进方向——成员从左到右按点位取值的消费机制未动，旧合法程序语义不变、仅"数量恰好匹配的多槽"由编译错转为合法，零 breaking。

防歧义的代价由**成员形态限制**支付：管道成员的匿名消费仅认裸 `_`，带洞运算式（`_ + 1` 类）不入成员位——运算符组合不出现在接口位置，消费顺序无从歧义；多参数消费只能来自有声明结构的单元（`@fn` 形参表、构造定义）。Scala `_` 独立绑定的教训吸收为"匿名槽必裸"；Kotlin `it` / Clojure `%` 的多引用先例在无共享绑定前提下不再构成风险。
